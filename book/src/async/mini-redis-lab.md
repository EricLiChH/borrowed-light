# mini-redis 迁移实验

| 任务 | 概念 | 预计时间 | 项目产物 |
|---|---|---:|---|
| 阅读并改造一个真实异步协议片段 | frame、task、channel、shutdown | 90–120 分钟 | 设计对照笔记 |

> **这是一次「读别人的异步代码」的训练，不是第二个主项目。** 本实验不复制上游代码，也不实现 Redis 数据库。

---

## 1. 为什么要读别人的异步代码

到目前为止，你写的异步代码都是自己的。真实工作里更常见的情况是：**接手一个陌生仓库，判断它的任务边界在哪里、取消会不会留半成品。**

读异步代码有一个和读同步代码不同的地方：**`.await` 的位置决定了并发结构**。同步代码里「谁在等谁」从调用栈就能看出来；异步代码里，两个函数可能挨着写，却在完全不同的任务上运行。

mini-redis 是这份训练的好材料：它只有几百行核心逻辑，却包含了真实服务器需要的全部形状——连接任务、共享状态、channel、优雅关闭。

## 2. 它长什么样

```text
                  ┌──────────────┐
   TCP 连接 ─────►│ connection   │  每个连接一个 task
                  │   task       │  解析 frame → 发请求 → 等回复
                  └──────┬───────┘
                         │ mpsc（有界）
                         ▼
                  ┌──────────────┐
                  │ manager task │  独占 HashMap<String, Bytes>
                  │              │  串行处理所有命令
                  └──────────────┘
```

这个结构值得注意的地方：**共享的 `HashMap` 没有被锁保护，而是被一个 task 独占。** 所有访问都变成消息，于是「并发安全」由「只有一个所有者」保证，而不是由锁保证。

这正是本书第 3 节讲的提问顺序（独占 → 消息 → 共享状态）在真实项目里的样子：**能用前两种，就不要用第三种。**

## 3. 三次定向修改

联网时打开 [Tokio mini-redis 教程](https://tokio.rs/tokio/tutorial/setup)，完成 setup、spawn 与 channels 三节；**离线时用本书前两章的 channel 示例完成同样的三次修改**（结论一致）。

### 修改一：画出任务边界

问：哪些值 move 进 task？哪些通过 `Arc` 共享？为什么？

写完对照表再看下一节：

| 值 | 怎么过去 | 为什么 |
|---|---|---|
| `TcpStream` | move 进连接 task | 每个连接只属于一个任务 |
| `Db`（共享状态句柄） | clone 后 move（内部是 `Arc`） | 多个连接需要访问同一个 manager |
| 请求 / 响应 | 通过 channel 传递 | 避免共享可变状态 |

### 修改二：把无界 channel 改成容量 8

观察发送者在队列满时的表现：**它会进入 `Pending` 而不是阻塞线程**（[channel 章节](channels-cancellation.md)里验证过同一件事）。

记录三件事：谁在等、等的时候线程去做什么、如果永远不消费会发生什么。

### 修改三：加 shutdown 信号

在每个 `.await` 处标注：如果在这里被取消，会不会留下半完成状态？对照[取消安全检查表](channels-cancellation.md#4-取消安全检查表)：

| 操作 | 取消安全 | 判断依据 |
|---|---|---|
| `recv().await` | ✅ | 要么收到，要么没动过 |
| `send().await` | ✅ | 要么入队，要么没入队 |
| 读完半条 frame | ❌ | 已读字节无处安放 |

## 4. 迁移回健康监测器

把观察映射回本项目，写一页对照笔记：

| mini-redis | 网站健康监测器 |
|---|---|
| 连接 task | 单目标检查（`HealthChecker::check`） |
| manager task | 批量调度（`check_all` 的并发窗口） |
| 有界 channel 容量 | `concurrency` 预算 |
| shutdown 信号 | Axum 优雅关闭 |
| frame 解析 | HTTP 往返（由 `reqwest` 承担） |

**关键差异值得写进笔记**：mini-redis 的 manager 独占状态所以不需要锁；而本项目的 `InMemoryRepository` 需要 `RwLock`，因为 HTTP 请求是并发进入的、没有单一管理者。**同样是"共享状态"，选哪种形状取决于访问模式。**

## 5. 完成证据

不是「服务器跑起来了」，而是能回答这三个问题：

1. 为什么一个共享 `HashMap` 适合由单独 manager task 独占？
2. 为什么 HTTP 检查适合由多个受限 task 独立推进，而不需要一个中央调度者？
3. 如果给 mini-redis 加一个「定时清理过期键」的任务，它会与 manager 形成什么关系？（提示：还是消息，不是锁）
